# 开发方法论（mini-alpha）

> 这份文件不是"流程清单"，是**能推出清单的那一层**。
> 13 个阶段（需求 / 设计 / 方案 / 编码 / 白盒 / 黑盒 / 部署 / CI / CD / 灰度 / 监控 / 报警 / 定位 / 日志）
> 都是下面这条公理的**推论**，不是并列的条目。

---

## §0 公理

> **任何结论，都必须能在别人的机器上、用别人的数据、被机器重新验证一遍。**

凡是不能满足这句话的东西，都不是"结论"，只是"我这台机器上的一次观测"。

推论（每一段流程都从这条推出来）：

| 阶段 | 它其实在回答 |
| :-- | :-- |
| 需求 | 要验证**什么**？不做会怎样？ |
| 设计 | 验证的**边界**在哪？会波及谁？ |
| 方案 | **怎么算通过了**（每一条都要能写成判定） |
| 编码 | 写出**可被验证**的最小实现 |
| 白盒 | 内部每个分支都对吗 |
| 黑盒 | 对外行为（含边界/非法输入）都对吗 |
| 部署 | 东西能被别人拿到吗（版本/依赖/数据） |
| CI | 每次改动都自动验证了吗 |
| CD | 验证通过后能不能自动产出可用物 |
| 灰度 | 小范围内先验证，再扩大 |
| 监控 | 运行中还能被验证吗 |
| 报警 | 验证失败时**会吵**吗（而不是静默） |
| 定位 | 失败时能查到**哪一步、哪一格**吗 |
| 日志 | 上面这些的**证据**留下来了么 |

---

## §1 三段式主线

任何一次开发，只有三件事：

    【说清楚】 需求 → 设计 → 方案        ⇒ 我要验证什么，怎么算过
    【做出来】 编码                     ⇒ 能被验证的最小实现
    【证明它对】 白盒 → 黑盒 → CI → CD → 灰度 → 监控 → 报警 → 定位 → 日志
                                       ⇒ 证据链（每多一条，可信度多一层）

**关键认知**：第三段不是"额外工作"，**它是唯一能证明第一段没白写的东西**。

---

## §2 13 段 = 4 个动作的组合

所有阶段，本质都只是在做这四个动作之一（或组合）：

| 动作 | 含义 | 在各阶段的化身 |
| :-- | :-- | :-- |
| **① 固定输入** | 版本/数据/夹具/种子锁死 | 部署（版本）· CI（环境）· 灰度（同一份数据）· 复现测试夹具 |
| **② 写死判据** | 什么算过，机器能判 | 方案（验收标准）· 白盒（分支）· 黑盒（黄金值/边界）· 监控（阈值）· 报警（断言） |
| **③ 留下证据** | 事后能追 | 日志 · 内容指纹 · DIAG dump · 测试报告 · BASELINE.md |
| **④ 设一道门** | 不满足不许往下 | 需求签字 · 方案签字 · CI 必须绿 · 提交前全量测试 · 灰度未过不许出结论 |

> **判断一个流程是不是"生产级"**：随便挑一个阶段，问"这四件事它做了几件"。
> **缺 ④（门）的流程 = 走形式**；**缺 ② 的流程 = 无法判定**。

---

## §3 裁剪法则（唯一一条）

> **"如果它错了，我要多久才能发现？"**

| 发现所需时间 | 流程档位 | 走哪几段 |
| :-- | :-- | :-- |
| 立刻（跑一次就知道） | **小** | 需求 → 编码 → 黑盒 → CI → 日志 |
| 几小时内 | **中** | + 方案（验收标准）→ 白盒 → 定位 |
| **几天到几周**（结论会被写进研报） | **大** | **全走** |

**为什么这条法则有效**：流程的成本基本固定（几小时），而错误的成本随"发现延迟"指数上升。
⇒ 裁剪的本质不是"省事"，是**把钱花在发现得晚的地方**。

---

## §4 agent 协作适配法则

> **一个 agent 只负责"产物能被机器判定对错"的那一段。**

| 段 | 谁做 | 理由 |
| :-- | :-- | :-- |
| 需求 | **人** | 只有人知道"为什么" |
| 设计/方案 | **agent**（planner） | 产物是文字规格，且**每条能写成测试** |
| 编码 | **agent**（builder） | 产物是代码，有测试兜底才敢放 |
| 白盒/黑盒 | **agent**（reviewer） | 完全可判定 |
| 部署/灰度/发布 | **人** | 责任不可转移 |
| 定位 | **agent 提证据 + 人下结论** | 结论必须人签字 |

**通信纪律**（本环境硬约束）：

- 只能直系父子通信 ⇒ **星形拓扑**，所有跨 agent 消息经 main 中转
- main 只做 3 个决策：**去哪儿 / 要不要问人 / 回流失没到上限**
- main **不做技术判断**（技术判断归 reviewer 和人）
- **真正的记忆在文件里**，不在任何 agent 的上下文里（换 agent = 丢上下文）

**回流规则**：

    测试红了        → 回 编码
    review 发现隐患 → 回 编码；若是"需求没定义" → 回 方案
    同一个 bug 回流最多 2 次；第 3 次 ⇒ 判定为"规格错了"，强制回 方案
    每次回流必须【新增一条会在旧代码上红的测试】

---

## §5 三个 agent 专属失败模式

| 失败模式 | 表现 | 对策 |
| :-- | :-- | :-- |
| **共识漂移** | 5 个 agent 都说"没问题" —— 因为都基于同一份错的 brief | 下一段必须**独立复核关键事实**（自己读代码），不只复核结论 |
| **假完成** | agent 说"已完成"，实际 80% | 出口条件必须**机器可判定**：pytest 50/50 而不是"实现完成" |
| **回流震荡** | A 改坏 B，B 改坏 A | 回流上限 2 次 + 每次必须新增测试 |

## §6 成熟度自评（五级）

| 级 | 特征 | 你的状态 |
| :-: | :-- | :-- |
| 1 | 能跑，但结果不可复现 | 已过 |
| 2 | 结果可复现（固定输入） | 已过（面板缓存指纹） |
| 3 | 有判据，失败会吵（断言/测试） | **2026-10-19 到达这里** ✅ 33 个测试 + 9 道断言 |
| 4 | 门禁自动化（CI + 提交前全量） | 差一步：CI 只覆盖 16 个纯函数（数据不在仓库） |
| 5 | 可定位到"哪一格"（指纹/DIAG/链路） | 部分：指纹有了，DIAG 只在崩溃时打 |

> **通往第 5 级的唯一路径**：把"证据"从"崩溃时打"改成"每次都打"。
> 代价是日志变多，收益是**不用等崩溃就能发现问题**。

## §7 每段的"最小产物"

    需求     docs/dev/T-xxx/00_ticket.md      一段话：为什么做，不做会怎样
    设计     docs/dev/T-xxx/01_brief.md       数据流向 + 影响面（动哪几个文件）
    方案     docs/dev/T-xxx/02_spec.md        验收标准（每条可测）+ 不做清单 + 我的 3 个疑问
    编码     diff + 03_impl.md                改了哪些文件 + 每个决定的理由
    白盒     qa/test_unit_*.py                纯函数对拍（不需要数据）
    黑盒     qa/test_acceptance.py            黄金值 + 边界注入
    部署     git tag + BASELINE.md            这次发布对应的数字基线
    CI       .github/workflows/ci.yml         push 自动跑
    CD       全量 pytest + 压测报告            通过才能出结论
    灰度     单因子 → 6 因子 → 100 次压测       分阶段扩大
    监控     logs/run.log 里的 fp / 关键数字
    报警     raise（断言）                    绝不静默
    定位     DIAG dump + 指纹对账
    日志     loguru（结构化 + 关键上下文）

---

## §8 每日节奏（推荐）

    开工   ：选一张 ticket（人）→ 人写 00_ticket.md
    上午   ：planner 产 01_brief.md → 产 02_spec.md → 【人签字】
    下午   ：builder 编码 → 人审（五条清单）→ reviewer 隐患清单 → 测试
    收工前 ：python -m pytest（26 秒）→ commit → 【main 总结 + 敲定下一步】
    每周   ：一次 100 次压测（稳定性）→ 必要时 git tag + 更新 BASELINE

**人的四个签字点**（不可外包）：

    ① ticket（为什么要做）
    ② spec（怎么算做完了）
    ③ 编码审查（五条清单：口径/断言/边界/错误路径/可观测）
    ④ commit（责任）

---

## §9 人的五条审查清单（沿用于所有任务）

    ① 口径：成交价 / 成本 / 换手 / 年化 —— 有没有偷偷变？
    ② 断言：坏数据当场停，还是静默算错？
    ③ 边界：空数据 / 全 NaN / 只有 1 只 / 列顺序乱 —— 会怎样？
    ④ 错误路径：失败时日志能不能定位（还是要靠猜）？
    ⑤ 可观测：关键数字打出来了吗？有指纹吗？

---

## §10 一句话总结

> **13 段流程是"证据链"，不是"工序"。**
> 证据链的每一环只在回答一个问题：**"凭什么信这个结论？"**
> 而裁剪的唯一依据是：**"如果它错了，我要多久才发现？"**
