# 通用工程合约

## 1. 不可协商的四条

1. **不做没被要求的改动**。改 A 时发现 B 有问题 → 记进 REVIEW，不要顺手改。
2. **答案必须可复现**：结论要能在别人机器上重新算一遍得到同样数字。
3. **失败要吵，不许静默**。数据退化 / 结果越界 → raise，不产出报告。
4. **不确定就说不确定**，并标注：实测 / 文献 / 推断 / 待定。

## 2. 动手前必须先做的事

1. 读相关文件（不许凭印象改代码）。
2. 说清**影响面**：会波及哪些文件 / 哪个下游产物。
3. 说出**判据**：改完怎么算成功（一条能跑的检查）。
4. 如果判据写不出来 → 说明需求没想清，先问，不要开工。

## 3. 代码纪律

- 大数组（> 1000 万格）：先 `np.full` 铺满，再逐格写；**禁止** `np.empty`。
- 不把"写满数组"的责任交给库（rolling / where / ffill / reindex / loc / [cols] / corr / rank / copy）。
- 大数组交接：零拷贝，或拷贝后校验 + 重试。
- 日志里**禁止** `.get(key, 默认值)` —— 取不到就报错，别伪装成正常。

## 4. 测试下限（写代码时同步写，不许事后补）

1. 每个新函数：1 条正常路径 + 1 条错误路径。
2. 每个新分支：1 条边界。
3. 每个 bug 修复：**先写一条在旧代码上会红的回归测试**。
4. 每个对外接口：1 条"输入非法时会吵"。
5. 改完必须跑：`python -m pytest`（全量，不许只跑 -k）。

## 5. 交付格式

- 先说结论，再说证据（命令 / 输出 / 数字）。
- 改了哪些文件、为什么改，逐条列出。
- 明确写出"没做什么"和"不知道什么"。

## 6. 禁止事项

- 禁止为了让测试通过而放宽断言。
- 禁止把失败说成"已完成"。
- 禁止在没有验收标准的情况下改业务逻辑。
